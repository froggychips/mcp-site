mcp-skills-vault

A deterministic registry + integrity scanner for MCP servers, so installing one stops feeling like curl | bash. Sister project to mcp-trace.

Install

# One-line — no clone, no global install
npx -y @froggychips/mcp-vault scan --cwd ./my-project    # what to install for this stack
npx -y @froggychips/mcp-vault list                       # all 114 servers in the DB
npx -y @froggychips/mcp-vault audit --strict             # diff installed vs DB
npx -y @froggychips/mcp-vault verify --offline           # true offline DB-pin gate
npx -y @froggychips/mcp-vault doctor                     # local readiness check

# Prefer it on PATH? Drop the npx prefix after this.
npm i -g @froggychips/mcp-vault

# As a Claude Code skill (optional)
git clone https://github.com/froggychips/mcp-skills-vault.git
mkdir -p ~/.claude/skills
cp -r mcp-skills-vault/mcp-ecosystem-intelligence ~/.claude/skills/

Zero runtime dependencies. Node built-ins only. One JSON file is the entire database.

What you get

  • Curated DB — 114 entries across 26 categories, all with pinned versions and SPDX licenses. 20 Core / 71 Recommended / 23 Experimental. trust is derived from dated evidence rather than typed by hand: 101 verified, 1 candidate, 12 unverified — the 12 being eight entries with an advisory against the pinned version, two whose repository disagrees with the registry’s, one yanked and one unpublished.
  • Browse it — mcp-vault list shows every entry with name / category / tier / trust / install command. Filters: --category, --tier, --trust, --query. --json for scripts.
  • Supply-chain gate that fails closed — sha512 (npm), sha256 (PyPI) and @sha256: (Docker) pins, re-verified against the live registry, with 4 advisory feeds merged (npm bulk + OSV.dev + GHSA + Snyk) before the install command is written. Anything it could not check reports UNVERIFIED rather than passing: a feed being down is not evidence that a pin is good.
  • Hash the bytes yourself — --deep downloads each artifact and hashes it locally instead of comparing the pin against metadata served by the same host as the tarball. npm’s registry signature over name@version:integrity is verified on every run (100 of 102 npm entries today), and provenance attestations are read and compared with the recorded source repository.
  • The whole dependency tree — --deps resolves it with npm install --package-lock-only --ignore-scripts (nothing installed, no package code run) and checks every package in it. Across the DB that is 19,377 transitive packages, 25 entries whose dependencies run install scripts, and 38 with a high or critical advisory somewhere in the tree.
  • What actually gets written — install writes the version the gate verified (pkg@1.2.3, pkg==1.2.3, image@sha256:…), and refuses an unpinned command. npx -y pkg resolves latest at every start, which is not the artifact anyone reviewed. --host targets Claude Code, Claude Desktop, Cursor, VS Code, or prints a TOML block for Codex.
  • Check what your hosts really launch — mcp-vault verify --installed reads the configs themselves instead of the DB, and reports unpinned commands, servers that are not in the vault, local binaries and remote endpoints as what they are.
  • Trust as dated evidence — each dimension (artifact, signature, provenance, source binding, advisories, dependencies, smoke) carries its own status and the date it was established, with its own shelf life: a hash match holds for 90 days, “no advisories” for 7. trust is derived from that, and dropped when the version moves.
  • One policy file, not seven flags — .mcp-vault.policy.json sets the bar once (unverified handling, signature and provenance requirements, licence allow/deny, minimum health, acceptable trust tiers) so CI and your shell enforce the same one. An unknown key is an error, not a no-op.
  • Behavioural smoke — mcp-vault eval --sandbox spawns a server jailed in an ephemeral container, runs the initialize → tools/list handshake, counts tools and lints each schema. A docker run entry is rebuilt from its pinned digest under the jail’s own flags, because the entry’s flags come from a file a pull request can edit. The hash proves you got the file; this proves the file starts.
  • Context budget — mcp-vault budget totals what your configured servers inject into every request, stating for each number whether it was measured from a real tools/list payload or estimated from a tool count.
  • Machine-readable — --json for every command, and verify --sarif so each finding lands on the tools_database.json line that caused it in GitHub code scanning.
  • Audit installed setup — mcp-vault audit diffs your installed servers against the DB and flags drift, untrusted entries, heavy-unbounded servers, and scope issues.
  • Doctor — mcp-vault doctor checks Node, gh, Docker, uvx, and Claude MCP config readiness without printing token values.
  • Is it still published? — mcp-vault availability tells gone, version-gone, yanked and deprecated apart, because a 404 and a network failure arrive on the same code path and both used to read as “could not check”. One entry in this DB had been unpublished from npm while still marked verified — and an unpublished name is not a broken link, it is a name somebody else can register.
  • Who published it — cross-referenced with the official MCP registry, whose namespaces are ownership-verified at publish time (io.github.<owner>/… requires authenticating as that account). Nothing else here is proved in that sense: npm’s repository.url is typed by the publisher and a vault entry’s source URL is typed by a pull request. Not a competing registry — a security overlay over one.
  • What the package can do, and what it gained — mcp-vault capabilities reads the published tarball in memory and records each capability with a file and a line. Across the 99 npm entries it can read: 84 read process.env, 74 reach the network, 35 can run other programs, 31 run install scripts, 15 evaluate code built at runtime. Then it diffs against the previous version, because a patch release that starts shelling out is what a compromised release looks like before it has a CVE.
  • Did the tools change? — every passing behavioural run fingerprints the tool surface per tool (name, description and input schema hashed separately, hashes only). It also records the identity of what ran, so a later run can say which of three things happened: the surface changed with a new artifact (an upgrade), changed without one (unexplained — the case worth looking at), or cannot be attributed because nothing recorded an identity to compare. “Unexplained” is not “impossible”: an unvendored launch re-resolves its dependency tree at every start, and flags, credentials and a remote backend can each change what a server advertises.
  • So what do I install instead? — mcp-vault upgrade computes the shortest version that clears every advisory against a pin, not the newest release, and queries the candidate too — “fixed in 2.1.30” means fixed for that advisory. All eight affected entries in this DB have a safe path today.
  • Why was it denied? — mcp-vault explain <name> prints every dimension with the date it was established and whether that date is still inside its shelf life, the policy in force, each rule with its outcome, and the rule that decided it. --record appends the decision as one JSON line, which is the audit trail a policy engine gets asked for six months later.
  • Freeze what actually runs — the gate verifies a package and its tree, then npx -y pkg@1.2.3 re-resolves that tree at every start: a pinned root does not pin its dependencies. mcp-vault lock records npm’s own lockfile per server, --check diffs a fresh resolve against it, and --vendor installs the locked tree so nothing resolves at launch.
  • Upstream repository posture — OpenSSF Scorecard read through deps.dev: branch protection, code review, dangerous workflow triggers, token permissions, pinned actions, signed releases. Recorded as individual checks rather than Scorecard’s 0–10 average, and its “could not run this check” is recorded as unknown, never as a failure. Coverage is stated rather than implied: 4 of 114 repositories have a report.
  • SBOM — mcp-vault sbom emits CycloneDX 1.6 (validated against the official schema), carrying what this tool knows and CycloneDX has no field for: the trust tier, each evidence dimension with its date, which dimensions have aged out, the behavioural status, and for transitive packages whether they run code at install time.

What this does NOT do

  • Not a sandbox. Installing an MCP server still runs that server with the permissions of your MCP host.
  • Not a runtime monitor. Vault is an install-time gate; use mcp-trace or another monitor for runtime behaviour.
  • Not proof that a server is benign. Hashes prove you got the artifact you expected, not that the artifact is safe.
  • Provenance is bound, not cryptographically verified. bound means npm’s own registry signing key — the same key dist.signatures is checked against — signed a DSSE statement whose subject digest is the artifact we verified, and a certificate claims the recorded repository built it. The DSSE signature is checked, so swapping the digest in an attestation document does not pass. What is still not done: the Fulcio certificate chain is not validated and the Rekor inclusion proof is not checked, which is why the identity half stays a claim about a repository — anybody can mint a certificate with any name in it. That asymmetry is the reason the digest half has to rest on npm’s key, and the word “verified” never appears next to provenance.
  • A capability scan shows presence, never absence. Eighteen of the ninety-nine readable packages ship at least one minified file; obfuscated code, a dynamic require and a string built at runtime all defeat a pattern scan. So a capability found is a fact with a file and a line, a capability not found is recorded as nothing at all, and a capability that stops matching between versions is reported as “may be a change in behaviour, or only in readability” rather than as an improvement.
  • Behaviour is measured in a clean container, which is not your machine. 40 of 113 entries complete a handshake there; the rest crash, time out, or want credentials and network they are not given. That caps a recommendation rather than condemning a server: “needs credentials” is a setup step, “never started” is a reason to look before installing.

Latest release

v0.14.0 — 2026-09-17

  • Trust stopped being a word somebody typed. The evidence model is filled for the whole database: eight dimensions, each with the date it was established and its own shelf life, and trust computed from them — 101 verified, 1 candidate, 12 unverified. The 12 are specific: eight advisories against a pinned version, two repositories that disagree with the registry’s, one yanked release, one unpublished package.
  • One of four advisory feeds had never worked. npm’s bulk endpoint was being sent an array containing an empty string as the version, under a comment claiming npm tolerates it. It answers HTTP 400. Fixed, and it now asks about the pinned version, which is what the endpoint is for.
  • Provenance is bound to the artifact — the attestation’s subject digest is compared with the integrity value the registry signed, and the signing certificate’s identity with the recorded repository. 45 entries reach that state. What is still unchecked is stated in the output rather than implied away.
  • Behaviour decides whether something is recommended. The eval has recorded whether a server completes a handshake all along — 40 of 113 do — and nothing read it at the point a recommendation was printed. “Never started” now caps a verdict, “needs credentials” reads as a setup step, and both say why.
  • New checks: availability (gone / yanked / deprecated / relocated), identity (the official registry’s ownership-verified namespace), capabilities (what a package can do, with the version-to-version delta), posture (OpenSSF Scorecard for the upstream repo), upgrade (the shortest version clearing an advisory), explain (the decision, the evidence and the rule that made it), lock (freeze the tree; --vendor so nothing resolves at launch) and sbom (CycloneDX 1.6).
  • Tool-surface fingerprints — 1,021 tools across 40 servers, hashed per tool, so a renamed tool or a rewritten description is visible. A change is attributed to a new artifact, reported as unexplained, or declared not attributable — the third answer being the one a string comparison could not give.
  • The documented numbers are tested against the data. Fifteen claims on the README, checked on every run — the tier distribution had read 20/76/18 for a database holding 20/71/23.
  • Twenty-one defects found by review before release, most of them the same shape: a comparison that looked like a proof. The attestation’s subject digest was read out of an unauthenticated document; a hand-written tar parser could be made to loop forever by an archive declaring a negative size; every PEP 440 suffix combination ordered wrongly, which for an upgrade planner means naming a version that is still vulnerable; --vendor re-resolved the tree it was supposed to be installing. CodeQL, newly enabled, added five more on its first run.
